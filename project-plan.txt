1. App name and short description
Tech It & Go! - a full-stack app that helps makerspaces, nonprofits, and educators browse technology kits, submit borrowing requests, and find related lesson plans.

Project proposal
I plan to build a technology lending library that connects my background in libraries and makerspaces with my software engineering studies. The collection will include 3D printing kits, robotics, computers, coding resources, emerging technology, and entrepreneurship tools. Software records describe license terms and authorized access; the app does not redistribute software licenses. Large fabrication equipment can be listed as on-site use only.

My MVP includes a home page, catalog, search and filters, item details, related lessons, equipment CRUD, a lending request form, database persistence, responsive styling, and deployment. A request is pending, not a confirmed reservation. Availability is a staff-maintained current quantity; automatic date-based inventory and approvals belong in the Icebox.

Technologies: React with Vite, JavaScript, HTML, CSS, React Router, Node.js, Express, MongoDB Atlas, Mongoose, bcrypt, jsonwebtoken, dotenv, fetch, Git/GitHub, VS Code, and Postman. Colors: hot pink, teal/Tiffany blue, soft purple, mint, black, and white.

Scope note: admin screens describe the collection manager workflow. In a public deployment, equipment write routes must be protected by staff authentication/authorization before enabling edits. Email/password authentication with bcrypt, JWT login, a protected personal dashboard, paginated lists, and user-owned request CRUD are required MVP features. Advanced checkout tracking remains future scope.

4. ERD and data flow

All equipment has many LessonPlans and many LendingRequests. Each lesson and request references one equipment item using a MongoDB ObjectId. Categories are an enum field on Equipment, not a separate collection. User has many LendingRequests. Each request includes an ownerId reference to User; borrower identity is derived from the authenticated account.

    string role
  }
  EQUIPMENT   --o{ LESSON_PLAN : supports
  EQUIPMENT   --o{ LENDING_REQUEST : receives
  EQUIPMENT {
    ObjectId _id PK
    string name

    ObjectId _id PK
    ObjectId equipmentId FK

    string steps
    string skillLevel
  }
  LENDING_REQUEST {
    ObjectId _id PK
    ObjectId equipmentId FK
    ObjectId ownerId FK
    string borrowerName
    string borrowerEmail
    date checkoutDate
    date returnDate
    string purpose
    string status
    date createdAt
  }

Data flow: React sends an HTTP request to Express. Express validates the input, uses Mongoose to read/write MongoDB, and returns JSON. React updates the screen. Borrowing requests do not decrement stock automatically. Related lesson records are seeded in the MVP; lesson editing is future scope.

Validation: require equipment name/category/description and nonnegative integer quantity; validate request email and dates (return after checkout, checkout not in the past); require a real active equipment reference. On-site-only items display an on-site-use message rather than a take-home request. Show 400 for invalid input, 404 for missing records, and a safe 500 response for unexpected errors.

5. User stories and acceptance criteria

1. As a visitor, I want to browse technology equipment so I can find resources for my program.
   Acceptance: Catalog shows names, categories, images, descriptions, and quantities.

2. As a visitor, I want to search and filter equipment so I can find a suitable kit quickly.
   Acceptance: Search matches name/description; filters apply category and current availability.

3. As an educator, I want to view item details and related lessons so I know how to use the equipment.
   Acceptance: Details show skill level, safety notes, and linked lesson objectives/materials.

4. As a borrower, I want to submit a lending request so staff can review my proposed borrowing dates.
   Acceptance: Valid name, email, dates, and purpose save a pending request; success shows a confirmation.

5. As a collection manager, I want to add equipment so new resources appear in the catalog.
   Acceptance: Valid required fields create a MongoDB record and appear after refresh.

6. As a collection manager, I want to edit equipment so its information stays accurate.
   Acceptance: Changes persist after refresh; quantity cannot be negative.

7. As a collection manager, I want to remove retired equipment so visitors see the current collection.
   Acceptance: Delete requires confirmation; records with requests are archived instead.

8. As an educator, I want to browse lesson plans so I can plan hands-on learning activities.
   Acceptance: Lesson list and detail pages show title, objectives, steps, materials, and skill level.

6. RESTful routes

  Method   Endpoint   Purpose  

  GET   /api/equipment   List active equipment; optional search, category, available filters  
  GET   /api/equipment/:id   Read one equipment item  
  POST   /api/equipment   Create equipment  
  PATCH   /api/equipment/:id   Update equipment fields  
  DELETE   /api/equipment/:id   Delete unused item; archive if requests reference it  
  GET   /api/lessons   List lesson plans; optional equipmentId filter  
  GET   /api/lessons/:id   Read lesson plan details  
  POST   /api/requests   Save a pending lending request  
  GET   /api/health   Check server readiness without exposing secrets  

Equipment POST/PATCH/DELETE are staff-only in a public release. Request endpoints require login and return only the authenticated user's records. Users can list, edit, and delete their own pending requests. Approval routes are future scope. Successful create returns 201; reads/updates 200; delete 204.

API additions

Use domain-specific routes below. The class's /api/items endpoint is an example; here the user's personal items are lending requests.

  Method   Endpoint   Access / purpose  

  POST   /api/auth/register   Public; normalize email, validate fields, bcrypt hash; never accept a client-supplied staff role  
  POST   /api/auth/login   Public; verify credentials and return JWT with safe user fields  
  GET   /api/auth/me   Authenticated; return current user without password hash  
  GET   /api/requests?page=1&limit=10   Authenticated; owner-filtered, paginated personal list  
  POST   /api/requests   Authenticated; create request with ownerId from verified token  
  PATCH   /api/requests/:id   Authenticated; edit only owned pending requests  
  DELETE   /api/requests/:id   Authenticated; delete only owned pending requests  

Return a pagination object with page, limit, total, and totalPages. Validate positive integer query values and cap limit at 50. Use a stable sort before skip/limit. Clamp the dashboard page after deletion when the last record on a page disappears.

Model and authorization details
User: name, unique normalized email, passwordHash excluded from normal queries, role (borrower/staff), timestamps.
LendingRequest: ownerId references User; equipmentId references Equipment; checkoutDate, returnDate, purpose, pending status, timestamps.

Preserve equipment and lesson relationships. Equipment quantity is a nonnegative integer; onSiteOnly and archived are booleans.
Query request mutations by both _id and ownerId. A guessed ID must not expose or modify another user's records.
Allowlist editable fields; users cannot change ownerId, role, or approval status.
Handle duplicate-key email errors as form-friendly conflicts. Keep JWT_SECRET and MongoDB credentials in backend environment variables; commit only .env.example.

Reject expired/invalid JWTs; clear client token on authentication failure. React sends Authorization: Bearer TOKEN on protected requests.

localStorage is used to meet the supplied rubric; never render untrusted HTML or place database credentials/secrets in frontend code.
